# 경계면 교차 검증 절차

통합 테스트는 백엔드가 스스로 일관적인지 검증한다. 하지만 **백엔드가 완벽하고 프론트가 완벽해도 둘의 계약이 어긋나면 화면은 깨진다.** 이 문서는 그 불일치를 찾는 절차다.

빌드 통과나 테스트 통과로는 잡히지 않는다 — 프론트가 JS라 타입 검사가 없고, 백엔드 테스트는 프론트 코드를 모른다.

## 목차

1. 핵심 원칙 — 양쪽 동시 읽기
2. 검증 대상 경계면 5종
3. Playbook 고유 불일치 패턴
4. 절차

## 1. 핵심 원칙 — 양쪽 동시 읽기

한쪽만 읽으면 반드시 놓친다. "API가 존재하는가"와 "API의 응답이 호출측 기대와 일치하는가"는 완전히 다른 검증이다.

| 검증 대상 | 왼쪽 (생산자) | 오른쪽 (소비자) |
|----------|-------------|---------------|
| 응답 shape | 컨트롤러 `ResponseHandler.success(x)` + `x`의 DTO 필드 | `api/*.js` 호출부 → 컴포넌트의 `res.data.data.*` 접근 |
| 엔드포인트 | `@GetMapping` 등 매핑 경로 (+ `context-path=/api`) | `api/*.js`의 URL 문자열 |
| 권한 | `AuthUtil.requireX` + 인터셉터 화이트리스트 | 프론트 탭·버튼 노출 조건 |
| 데이터 흐름 | 테이블 컬럼 → 엔티티 `@Column` | DTO 필드 → 프론트 접근 키 |
| 상태 코드 | `ResponseCode` enum | `statusMapper.js` / `constants.js` |

**존재 확인 체크리스트는 약하다. 교차 비교 체크리스트를 쓴다.**

| 약함 | 강함 |
|------|------|
| 엔드포인트가 존재하는가? | 응답 shape이 프론트 접근 키와 일치하는가? |
| api 모듈에 함수가 있는가? | 그 함수가 실제로 컴포넌트에서 호출되는가? |
| 권한 게이트가 있는가? | 게이트 레벨이 프론트 노출 조건과 같은가? |
| DTO가 정의됐는가? | DTO 필드명이 엑셀 컬럼 키·차트 라벨과 일치하는가? |

## 2. 검증 대상 경계면 5종

### 2-1. 응답 shape ↔ 프론트 접근 키

```
1. 컨트롤러에서 ResponseHandler.success(x)의 x 타입 확인
2. x가 DTO면 필드명 목록 추출, List면 원소 타입까지
3. api/*.js에서 대응 함수 확인
4. 그 함수를 호출하는 컴포넌트에서 res.data.data 이후 접근 경로 추출
5. 필드명·중첩 깊이·배열 여부를 대조
```

가장 흔한 실패: 프론트가 `res.data`를 배열로 쓰는 경우. 실제로는 `{ code, msg, data }`가 들어와 `.filter is not a function`이 난다.

### 2-2. 엔드포인트 ↔ api 모듈 URL

```
1. 모든 @RequestMapping/@GetMapping/... 매핑 경로 수집 (클래스 레벨 + 메서드 레벨 결합)
2. 실제 URL = /api + 결합 경로  (context-path=/api)
3. front/src/api/*.js의 URL 문자열 수집
4. 양방향 대조:
   - api 모듈 URL 중 대응 엔드포인트가 없는 것 → 404 확정
   - 엔드포인트 중 프론트가 호출하지 않는 것 → 의도적(관리/스케줄러용)인지 누락인지 판단
```

### 2-3. 권한 레벨 ↔ 프론트 노출

```
1. 각 엔드포인트의 게이트 확인: getUser / requireAdmin / requireSuperAdmin / 없음
2. 게이트가 없으면 인터셉터 화이트리스트에 있는지 확인
3. 프론트에서 해당 기능의 노출 조건 확인 (탭 표시, 버튼 disabled)
4. 불일치 유형:
   - 백엔드 requireSuperAdmin + 프론트가 캠퍼스 관리자에게 노출 → 403 에러 화면
   - 백엔드 게이트 없음 + 프론트가 관리자만 노출 → 보안 취약 (security-auditor로 이관)
```

### 2-4. 컬럼 → DTO → 화면 필드명

```
1. 마이그레이션 SQL / 엔티티 @Column 컬럼명
2. DTO 필드명 (프로젝션 쿼리의 new 생성자 인자 순서까지 확인)
3. 프론트 접근 키, 테이블 헤더 바인딩, exportSheet 컬럼 키, 차트 라벨 키
4. snake_case → camelCase 변환 지점에서 오타·누락 확인
```

DTO 프로젝션(`SELECT new ...Dto(a, b, c)`)은 **인자 순서**가 생성자와 맞아야 한다. 타입이 같으면 컴파일도 통과하고 순서만 바뀐 채 잘못된 값이 나간다 — 조회 결과를 실제로 한 번 확인한다.

### 2-5. 상태 코드 ↔ 라벨 매핑

```
1. 대출 상태·계정 상태 등 코드 값의 도메인 정의 확인 (엔티티 enum, 상수)
2. statusMapper.js / constants.js의 매핑 키 확인
3. 정의된 모든 코드가 매핑되는가 (미매핑 → 화면에 원시 코드가 노출)
4. 매핑에만 있고 실제로 도달 불가한 상태가 있는가 (죽은 분기)
```

## 3. Playbook 고유 불일치 패턴

과거 실제로 발생했거나 구조적으로 발생하기 쉬운 것들. 매 검증에서 이 목록을 먼저 확인한다.

| 패턴 | 증상 | 확인 방법 |
|------|------|----------|
| **이중 래핑 누락** | `.filter is not a function`, `undefined` | 프론트가 `res.data.data`를 쓰는지 |
| **`/api` 접두사 오류** | 404 | api 모듈 URL이 `/api/`로 시작하고 중복되지 않는지 |
| **인터셉터 화이트리스트 누락** | 비로그인 화면에서 401 (실제 회귀 `09c744d`) | 공개 경로가 `LoginCheckInterceptor`에 등록됐는지 |
| **화이트리스트 과다** | 인증 없이 변경 API 통과 | `startsWith` 패턴 아래 POST/PUT/DELETE가 있는지 |
| **캠퍼스 스코프 불일치** | 남의 캠퍼스 데이터 노출 / 빈 목록 | `getCampusId(request, param)`가 파라미터를 검증 없이 쓰는지 + 프론트 필터 기본값 |
| **원시 타입 `@RequestBody`** | 415 / 400 | 프론트가 `Content-Type: application/json`을 명시하는지 (`favor.js` 참고) |
| **DELETE 바디** | 바디 누락으로 400 | axios `delete`가 `{ data: payload }` 형태인지 |
| **`@Where(use_yn='Y')` 누락** | 삭제 데이터가 화면에 다시 나타남 | 엔티티에 `@Where`가 있고, 삭제가 `setUseYn("N")`인지 |
| **LAZY 직렬화** | 500 / 무한 재귀 | 엔티티를 직접 반환하지 않고 DTO를 쓰는지 (`open-in-view=false`) |
| **엑셀 컬럼 키 불일치** | 빈 열 | `exportSheet.js` 키 == DTO 필드명 |
| **프로젝션 인자 순서** | 값이 뒤바뀜 | `new ...Dto(...)` 인자 순서 == 생성자 파라미터 순서 |

## 4. 절차

**점진적으로 실행한다.** 전체 완성 후 한 번 검증하면 초기 불일치가 후속 모듈로 전파되고 수정 비용이 커진다. 모듈(엔드포인트 묶음)이 완성될 때마다 그 범위를 즉시 검증한다.

```
1. 범위 확정 — 이번에 추가·변경된 엔드포인트와 화면 목록
2. 계약서(_workspace/02_contract.md) 확보 — 없으면 판정 기준이 약해지므로 그 사실을 명시
3. 경계면 5종을 순서대로 대조. 각 항목마다 양쪽 파일:라인 근거를 남긴다
4. Playbook 고유 패턴 11종 체크
5. 불일치 발견 시 계약서 기준으로 "어느 쪽이 틀렸는지" 판정하고 담당 지정
6. 리포트 작성
```

판정 원칙: **계약서가 기준이다.** 프론트를 고쳐 백엔드에 맞추는 것이 항상 정답은 아니다. 백엔드가 계약을 어겼다면 백엔드를 고친다.
